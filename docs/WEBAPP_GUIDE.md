# 커뮤니티 웹앱 제작 가이드

> 애기애타앱(교육 과정 원우 커뮤니티)과 뉴웨이브앱(청년부 사랑방 커뮤니티) 두 개를 만들며 정한 방식을
> 다음에 비슷한 앱을 새로 만들 때 그대로 참고할 수 있도록 정리한 문서입니다. 다른 컴퓨터의 다른 Claude
> Code 세션이 이 문서만 읽어도 "어떤 식으로 짜고, 어떻게 커밋·배포하는지" 감을 잡을 수 있게 쓰였습니다.
>
> 이 문서는 **새 프로젝트를 시작할 때 그 저장소에 복사해 넣고**, 그 프로젝트의 `CLAUDE.md`에서
> "먼저 이 문서를 읽으세요"라고 가리키는 방식으로 씁니다. `CLAUDE.md` 자체는 프로젝트 하나에만 붙는
> 파일이라(그 프로젝트를 열 때만 자동으로 불러와짐), 여러 프로젝트에 걸쳐 재사용할 안내서는 이렇게
> 별도 파일로 두는 것이 맞습니다.
>
> 값은 예시로 실제 두 앱이 쓴 수치를 보여 줍니다. 새 앱은 색·강조색만 바꾸고 구조는 거의 그대로
> 가져다 쓸 수 있습니다.

---

## 1. 이런 앱에 맞는 안내입니다

- **누가 쓰는가**: 명단이 정해진 작은 공동체(교육 과정 기수, 교회 청년부 등) 전용 비공개 커뮤니티.
  원우 명단·일정·채팅·투표·자료 같은 기능을 한 앱에 모읍니다.
- **어디서 쓰는가**: 거의 다 휴대폰 브라우저 → "홈 화면에 추가"한 PWA. 카카오톡 인앱 브라우저로도
  자주 열립니다(인앱 브라우저는 네트워크 요청이 이상하게 걸리는 경우가 있어 타임아웃 처리가 필요합니다).
- **디자인 방향**: 당근마켓·카카오톡처럼 한국에서 익숙한 앱 문법. 흰색·옅은 회색 바탕 + 강조색 하나.

## 2. 기술 스택

| 영역 | 선택 | 비고 |
|---|---|---|
| 프레임워크 | Next.js(App Router) + TypeScript | 최신 버전은 학습 데이터와 규칙이 다를 수 있음 — `node_modules/next/dist/docs/`를 먼저 확인 |
| 스타일 | Tailwind CSS v4 | `@theme` 블록에 디자인 토큰을 정의하면 유틸리티 클래스가 자동 생성됨 |
| 로그인 | Firebase Authentication | 구글, 카카오(서버에서 카카오 토큰 검증 후 Firebase 커스텀 토큰 발급), 휴대폰 문자 인증 |
| 데이터 | Cloud Firestore | 글·명단·대화 등 거의 모든 것 |
| 파일 | Firebase Storage 또는 Cloudinary | 사진은 브라우저에서 미리 줄여서 올림(프로필 정사각형, 사진첩 사진 긴 변 2000~2560px) |
| 서버 전용 로직 | Firebase Admin SDK (Next.js API 라우트) | 명단 가입 처리, 계정 합치기, 카카오 토큰 교환처럼 클라이언트가 직접 하면 안 되는 일 |
| 호스팅 | Firebase App Hosting | GitHub 저장소와 **연결돼 있지 않음** — push만으로는 배포 안 됨(아래 6장) |
| 알림 | 웹 푸시(FCM) | 서비스워커 라우트로 내려주고(아래 참고), VAPID 키 필요 |
| PWA | manifest + 스플래시 화면 | 앱을 열면 1~2초 강제 스플래시(브랜드색 바탕 + 로고)를 보여주고 그 뒤 화면을 그림 |

## 3. 디자인 토큰 — 색은 "이름"이 아니라 "역할"로

색을 `white`, `gray-200`처럼 색 이름으로 쓰지 말고 **역할 이름**으로 둡니다. 그래야 다크 모드에서
값만 바꿔 끼우면 됩니다. Tailwind v4의 `@theme` 블록에 정의하면 `bg-canvas`, `text-ink` 같은
유틸리티가 자동으로 생깁니다.

| 토큰 | 쓰는 곳 | 애기애타앱(주황) | 뉴웨이브(파랑) |
|---|---|---|---|
| `brand-500` | 유일한 강조색 — 주 버튼, 선택 탭, 링크 | `#FD5702` | `#0046FF` |
| `brand-ink` | 글씨·아이콘·밑줄처럼 "선"으로 쓸 때 (다크에서 500이 안 읽히면 더 밝은 값으로 분리) | `#FD5702` | 밝을 때 `#0046FF` / 어두울 때 `#6B93FF` |
| `brand-50~200` | 연한 강조색 배지·안내 상자·비활성 버튼 | 흰색 섞은 램프 | 흰색 섞은 램프 |
| `canvas` | 페이지 바탕(회색 화면) | `#ECECEB` | `#F1F4F9` |
| `surface` | 카드·시트·흰 화면 바탕 | `#FFFFFF` | `#FFFFFF` |
| `fill` | 흰 바탕 위 한 겹 옅은 회색(눌린 상태, 남의 말풍선) | `#F5F5F4` | 비슷한 값 |
| `field` | 흰 화면 위 입력칸 — **fill과 canvas의 정확히 중간**(`color-mix`) | — | — |
| `line` | 카드 테두리·구분선 1px | `#E4E6E9` | 비슷 |
| `ink` / `ink-soft` / `ink-muted` / `ink-faint` | 제목 / 버튼·아이콘 / 보조 글씨 / 흐린 글씨 (네 단계) | `#1C1917` 계열 | 비슷 |
| `danger` | 오류·삭제·"필수" | `#DC2626` | 비슷 |

**원칙**
1. **강조색은 하나만.** 필요하면 램프(50~500)만 늘리고, 어두운 단계(600~900)는 두지 않습니다 — 있으면 색이 탁해집니다.
2. **그림자 대신 1px 회색 테두리.** 번지는 그림자(글로우)는 기본적으로 쓰지 않습니다. 카드는
   `box-shadow: 0 0 0 1px var(--color-line)`로 그립니다(border 대신 box-shadow라서 모서리가 둥글게
   따라가고 크기가 안 커짐). 떠 있는 것(하단 탭바 등)만 예외로 살짝 그림자를 줄 수 있지만, "여러 겹
   글로우"는 십중팔구 나중에 "너무 입체적으로 보인다"는 되돌림 요청을 받습니다 — 처음부터 얇게.
3. **바탕과 카드의 명암은 늘 반대로.** 회색 화면 위엔 흰 카드, 흰 화면 위엔 회색 칸.
4. **다크 모드**는 `<html data-theme="dark|light">`(없으면 시스템 설정을 따름)로 전환하고, CSS 안에서
   `@media (prefers-color-scheme: dark) { :root:not([data-theme="light"]) {...} }`와
   `:root[data-theme="dark"] {...}` 두 블록에 다크 값을 미러링합니다. 강조색(brand-500)은 다크에서도
   그대로 쓰되, 대비가 부족하면(카드 배경 대비 5:1 미만) 글씨·아이콘 전용으로 더 밝은 `brand-ink`
   값을 따로 둡니다.
5. **접근성**: 흰 바탕 위 강조색 글씨가 대비 기준(4.5:1)에 못 미치면, 색을 어둡게 하지 말고 **굵게**
   하거나 **강조색 바탕 + 흰 글씨**로 뒤집습니다.

### 글자 크기 감각 (예시)

| 쓰임 | 크기·굵기 |
|---|---|
| 화면 제목(제목 줄) | 22px · 700 |
| 카드 제목 | 17~18px · 700 |
| 목록 이름 | 16px · 700 |
| 본문·입력칸 | 16~17px (**16px 밑으로 내리면 아이폰이 입력칸 누를 때 화면을 확대함**) |
| 보조 글씨 | 13~14px · 흐린 색 |
| 하단 탭 이름 | 11~12.5px · 500 |

### 모서리·간격 (예시)

| 토큰 | 값 |
|---|---|
| 홈 흰 박스 모서리 | 18px |
| 일반 카드 | 16px |
| 버튼·입력칸 | 14px |
| 시트 윗모서리 | 24px |
| 알약(하단 탭바 등) | `rounded-full` |
| 화면 좌우 여백 | 16px |
| 홈 박스 사이 | 13~14px |

## 4. 공통 화면 틀

### 4-1. 제목 줄 (PageHeader)
화면 맨 위 고정(`sticky top-0`). 왼쪽엔 뒤로가기(하위 화면일 때만) 또는 화면 이름, 오른쪽엔 알림·내
프로필·설정 세 아이콘. **바탕은 그 화면 바탕과 같은 색으로**(`tone="canvas"|"surface"`) — 어긋나면
스크롤할 때 제목 줄만 다른 색 띠로 떠 보입니다. 아이폰 상단 시계 줄 색은 화면 맨 위에 고정된 요소의
바탕색을 따라가므로, 이 규칙을 지키면 시계 줄도 자연히 맞습니다.

### 4-2. 하단 탭바 (떠 있는 알약)
- 흰 알약(`rounded-full`) + 1px 회색 테두리, 화면 아래에서 살짝 띄워 놓습니다(`safe-area-inset-bottom`
  고려). 탭 4~5개.
- 고른 탭: 아이콘 채워진 모양 + 강조색, 나머지는 선 아이콘 + 먹색. 칸 뒤에 옅은 회색 알약이 깔림.
- **그림자는 최소한으로.** 아예 없이 1px 테두리만 두거나, 필요하면 아래 방향으로만 은은한 그림자
  한 겹. 절대 "위 하이라이트 + 아래 그림자 + 안쪽 그림자"를 한꺼번에 쌓지 마세요.
- 본문 아래 끝에 탭바 높이만큼 여백을 둬서 마지막 내용이 가리지 않게 합니다.

### 4-3. 아래에서 올라오는 창 (시트)
- 화면을 반투명 막으로 덮고 흰 판이 아래에서 올라옵니다. 양옆·아래에 살짝 간격을 두고 네 모서리를
  모두 둥글게 하면(화면에 딱 붙지 않고 "떠 있는" 느낌) 더 고급스러워 보입니다.
- 맨 위 손잡이(작은 회색 막대) — 끌어내리면 닫힘. 바깥 막을 눌러도 닫힘.
- 아래 단추 한 줄: 왼쪽 흰 "취소" + 오른쪽 강조색 주 버튼.

### 4-4. 확인 창 · 작은 메뉴
- 삭제 같은 되돌릴 수 없는 동작은 반드시 확인 창을 거칩니다. 브라우저 기본 `confirm()`은 쓰지
  않습니다(아이폰 홈 화면 앱에서 주소가 찍힌 투박한 창이 뜸).
- "⋯" 눌러서 뜨는 작은 메뉴는 화면 밝기와 상관없이 늘 어두운 판 + 흰 글씨로, 되돌릴 수 없는 칸만
  빨강으로 구분합니다.

### 4-5. 빈 화면 · 불러오는 중
- 빈 화면: 가운데 정렬, 옅은 강조색 아이콘 → 제목 → 설명.
- 불러오는 중: 실제 목록과 **같은 짜임의 회색 스켈레톤**을 보여줘서, 불러온 뒤 줄 자리가 튀지
  않게 합니다.

## 5. Firestore 보안 규칙

- **"하나라도 허용하면 허용"** 방식입니다. `match /{document=**}` 같은 전체 허용 줄을 두지 말고
  컬렉션을 하나씩 명시합니다. 새 컬렉션을 만들면 규칙에 직접 추가해야 하고, 안 적으면 조용히 막힙니다.
- 서버(Admin SDK)만 읽고 쓰는 컬렉션(계정 합치기 기록 등)은 일부러 규칙에 적지 않습니다 — 클라이언트
  요청은 전부 거부되는 것이 의도입니다.
- **파일만 고쳐서는 효과가 없습니다.** `firebase deploy --only firestore:rules`로 게시해야 적용됩니다
  (아래 배포 스크립트가 함께 처리).
- 운영 권한(role)·차단 상태(status)는 화면에서 버튼을 숨기는 것만으로 막히지 않습니다 — 규칙이
  실제로 검사해야 합니다.

## 6. 커밋·배포 규칙 (두 앱 모두 이렇게 정했습니다)

이 절이 사용자가 가장 자주 확인하는 부분입니다. 다음 문장을 새 프로젝트의 `CLAUDE.md`에 그대로
옮기는 것을 권합니다.

1. **GitHub이 유일한 원본입니다.** 이 컴퓨터에만 있는 상태를 만들지 않습니다. 대화를 새로 시작하면
   먼저 `git status`·`git log`로 로컬이 GitHub과 같은지 확인합니다(다른 컴퓨터가 먼저 push했을 수
   있음 — 이런 경우가 실제로 있었습니다).
2. **무언가 고치면 묻지 않고 바로 커밋 + `git push origin main`까지 합니다.** push는 배포가 아니므로
   앱은 바뀌지 않습니다 — 그러니 매번 물어볼 필요가 없습니다. 커밋 전 연락처 같은 개인정보나
   `.env.local`·서비스 계정 키가 섞이지 않았는지 확인합니다.
3. **배포는 사용자가 "배포해줘"라고 명시적으로 말할 때만** 합니다. 이때는 되묻지 말고 바로 진행합니다:
   1. 커밋 안 된 수정이 있으면(사용자와 같이 고친 것이면) 먼저 커밋
   2. `npm run build`로 빌드 확인
   3. `npm run deploy` — 아래 스크립트가 push → 보안 규칙 게시 → App Hosting 배포(3~4분 걸림, 되도록
      백그라운드로 돌림) → 캐시 비우기 → 새 판 확인까지 한 번에 처리
   4. 끝나면 배포된 주소가 새 판을 보여주는지 확인하고 사용자에게 알림
   - ★ **App Hosting은 GitHub 연결이 아닙니다.** push만으로는 배포되지 않습니다 — 반드시
     `firebase deploy`(또는 그걸 감싼 `npm run deploy`)를 실행해야 합니다.
   - ★ Firebase CLI 로그인이 풀려 있으면 사용자에게 터미널에서 `firebase login`을 부탁합니다
     (브라우저 승인 필요, 에이전트가 대신할 수 없음).
4. **비밀값은 절대 커밋하지 않습니다.** `NEXT_PUBLIC_*`만 공개 가능(브라우저에 그대로 노출).
   서비스 계정 키·카카오 클라이언트 시크릿 같은 진짜 비밀은 Secret Manager에 두고, 호스팅 설정
   파일(`apphosting.yaml` 등)에는 이름만 참조합니다.
5. **작업 기록은 그 프로젝트의 `CLAUDE.md`나 코드 주석에 남깁니다** — Claude의 개인 메모(그 컴퓨터
   에만 있음)에 남기면 다른 컴퓨터에서 이어갈 수 없습니다. 값을 바꾸면 그 자리 주석에 **날짜와
   이유**를 남깁니다 — 1px 단위로 맞춘 값이 많아서, 이유 없이 되돌리면 다시 어긋납니다.
6. **새 컴퓨터에서 이어가기**: git·GitHub CLI 설치 → `gh auth login` → `gh repo clone` → 필요한
   런타임(Node.js 등) 설치 → `npm install` → `firebase login` → 환경변수 다시 만들기(`.env.local`은
   저장소에 없으므로 `apphosting.yaml`의 공개값 + Secret Manager의 비밀값에서 재구성, 또는 이 과정을
   자동화하는 `npm run setup:env` 스크립트를 만들어 둡니다).

## 7. 자주 걸리는 작은 규칙들

1. **입력칸 글씨는 16px 이상.** 아이폰은 16px 미만 입력칸을 누르면 화면을 확대합니다.
2. 전역으로 `button { font-size: 16px }` 같은 규칙을 둔다면, 그보다 작은 버튼 글씨는
   `text-[13px]!`처럼 **`!`(important)** 를 붙여야 이깁니다.
3. 한 줄에서 잘리는 글자는 CSS `text-overflow: ellipsis`(끝에 "…")만 되고, 가운데 높이 "⋯"는
   안 됩니다 — 카카오톡처럼 가운데 점을 쓰려면 칸 폭을 재서 직접 자르는 작은 컴포넌트가 필요합니다
   (`ResizeObserver` + 이진 탐색으로 들어가는 글자 수 계산).
4. `transform`이 걸린 상자 안의 `position: fixed`는 화면이 아니라 그 상자를 기준으로 섭니다 — 밀리는
   화면(스와이프 백 등) 안에 떠 있는 요소를 두지 마세요.
5. 한글 IME: 엔터 처리 전 `event.nativeEvent.isComposing`을 꼭 확인하세요(마지막 글자 빠짐·두 번
   전송 방지).
6. React 18+에서 effect 안에서 `setState`를 직접 하지 마세요(`react-hooks/set-state-in-effect` 린트가
   켜져 있으면 빌드가 멈춥니다). 브라우저 상태(온라인 여부, 로컬스토리지 등)는 `useSyncExternalStore`
   로 끌어옵니다.
7. 삭제·탈퇴처럼 되돌릴 수 없는 동작만 빨강으로 표시합니다. 다른 곳에 빨강을 쓰면 "조심"이라는
   뜻이 흐려집니다.
8. 카카오톡 인앱 브라우저 등 제한된 웹뷰에서는 네트워크 요청이 응답 없이 멈추는 경우가 있습니다.
   파일 업로드처럼 오래 걸릴 수 있는 요청에는 **시간제한(timeout)을 걸어** 무한정 로딩하지 않고
   실패로 처리해 사용자에게 알립니다.
9. 서비스워커(웹 푸시용)는 `fetch` 이벤트를 따로 안 걸면 다른 요청을 가로채지 않습니다 — 굳이
   가로챌 필요가 없다면 최소한으로 유지하세요.
